# 第一次回饋

## 第二題：不能改 GatewayPorts 時的替代做法

### 背景觀念：什麼是 sshd

sshd 是 SSH 的伺服器端程式（d = daemon，在背景一直跑的服務），跑在 VM 上，負責接收別人的 ssh 連線。SSH 分成兩端：

| | 程式 | 在哪裡 | 做什麼 |
|---|---|---|---|
| 客戶端 | `ssh` | 本地電腦 | 發起連線 |
| 伺服器端 | `sshd` | VM | 監聽 22 port、驗證身分、開 shell 給你 |

下 `ssh demo01@VM` 時，VM 上的 sshd 會收到連線，讀 demo01 的 `~/.ssh/authorized_keys` 確認金鑰在裡面，驗證通過後以 demo01 的身分開一個 shell。`/etc/ssh/sshd_config` 是它的設定檔，改完要 `sudo systemctl restart ssh` 才會生效。

和這個回饋的關係：

- 反向通道 `-R` 在 VM 上開的 port 是由 **sshd** 監聽，所以受 sshd 的 `GatewayPorts` 限制。
- 正向通道 `-L` 的 port 是由 **ssh 客戶端**監聽，不受 `GatewayPorts` 限制。
- 所以替代做法是在 VM 上 ssh 自己，讓 VM 自己當客戶端，再開一條 `-g -L`，繞過 sshd 的限制。

### 做法

第二題的做法要改 VM 的 `sshd_config`（`GatewayPorts clientspecified`），才能自己指定反向通道綁在 VM 的哪個 IP。如果沒有權限改 sshd 設定，但又需要用 VM 的 IP 連到這個服務，可以改用「兩段轉發」：

1. 本地：開反向通道，同時加上 `-A` 把本地的金鑰帶過去（agent forwarding）。沒有 GatewayPorts 時，VM 端只會綁在 `127.0.0.1:5433`：

   ```bash
   ssh -A -R 5433:localhost:5432 devbox
   ```

   - 第 2 步要在 VM 上 ssh 自己，需要一把能登入 danny 的金鑰，但私鑰只在本地。`-A` 讓 VM 上的 ssh 透過這條連線向本地借用金鑰，私鑰本身不會被複製到 VM。
   - 因為接下來要在這個連線裡繼續下指令，所以不加 `-N`（`-N` 只開通道、不給 shell）。
   - 前提是本地的 ssh-agent 有在跑，而且已經 `ssh-add` 加入金鑰（Windows 要啟動「OpenSSH Authentication Agent」服務）。可以用 `ssh-add -l` 確認。

2. VM（在第 1 步登入的 shell 裡）：自己再 ssh 自己一次，開一條加上 `-g` 的正向通道，把 `127.0.0.1:5433` 再轉到所有網卡上：

   ```bash
   ssh -N -g -L 5434:localhost:5433 localhost
   ```

   - 這一條通道由 ssh **客戶端**負責監聽，不受 sshd 的 GatewayPorts 限制。
   - `-g` 讓客戶端監聽的 port 綁在 `0.0.0.0`，而不是只綁 `127.0.0.1`。

3. VM：確認 port 已經綁在 `0.0.0.0`：

   ```bash
   ss -ltn | grep 5434    # 應看到 0.0.0.0:5434
   ```

之後用 VM 的 IP（或容器內用 `172.17.0.1`）加上 5434，就能連到本地的 Postgres。

注意：

- 綁在 `0.0.0.0` 代表所有連得到這台 VM 的人都能連這個 port，要靠防火牆限制來源。
- `-A` 連線期間，VM 上的 root 也能借用你的金鑰去登入其他機器，只對信任的主機使用。
